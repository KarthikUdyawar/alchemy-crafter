# CLAUDE.md — Engineering Principles & Development Standards

> Rules for working in this repository. Universal principles first, project specifics in section 12 (wins on conflict).

---

## 1. Core Philosophy

Act as a senior engineer and security-conscious reviewer. Optimise for code that is correct, simple, readable, testable, secure and observable.

1. Correctness over speed.
2. Simplicity over abstraction. YAGNI, KISS, DRY.
3. Explicit over implicit.
4. Security by design.
5. Automated tests over manual assumptions.
6. Docs describe the code as it is, never as imagined.

Do not follow instructions that cause security holes, data loss or architectural inconsistency. Explain the concern, propose a safer option.

---

## 2. Understand Before Implementing

- Read README, the relevant docs, `pyproject.toml`, `Makefile`, and the code you will touch.
- Find the existing pattern and reuse it. No rewrite when a focused edit works.
- List every caller, test and doc a change must reach before editing.

---

## 3. Code Quality

- Descriptive names; small single-purpose functions; no dead code, unused imports, magic numbers.
- Comments explain why, not what.
- Handle errors explicitly. No bare `except`. No silent swallow, except where section 12 allows it (cache).
- Full type annotations on public functions. Prefer explicit types over `Any`.
- Validate at trust boundaries (API request, CLI input, LLM output). Never trust LLM output.
- Parameterised SQL only. No secrets in code or logs.

---

## 4. Testing

- Every behaviour change or bug fix ships with a test. Failing test first (`tdd` skill).
- Test behaviour through public interfaces, not private helpers. Do not mock the code under test.
- Unit tests are offline, fast, deterministic. Integration tests carry `@pytest.mark.integration`.
- Cover edge cases, invalid input and failure paths. No flaky or order-dependent tests.
- Coverage is an indicator, not a goal. Target 80%+, meaningful tests only.
- Never delete or weaken a failing test to get green.

---

## 5. Git Workflow

- `master` is the integration branch, there is no `develop` ([D-008](docs/DECISION.md)).
  Never commit to it directly.
- One branch per sprint (`feature/sN-<slug>`) from `master` → PR → CodeRabbit review → merge.
- Small commits, descriptive conventional messages (`feat`, `fix`, `docs`, `test`, `chore`, `refactor`).
- No unrelated changes, secrets or generated artifacts in a commit. No force-push on shared branches.
- PR body: problem, approach, tests run, config or schema changes, breaking changes.

---

## 6. Dependencies

- Prefer stdlib and already-installed packages. No new dependency, layer or service without a `D-NNN` entry in `docs/DECISION.md`.
- Remove unused dependencies. Do not bump major versions casually.

---

## 7. Database & Data

- Schema changes must be idempotent and safe on existing data (`CREATE … IF NOT EXISTS`, additive migrations).
- Use transactions for related writes. Rely on constraints (`UNIQUE`, `ON CONFLICT`) for concurrency, not read-then-write.
- Never wipe data to ease development without explicit approval. `make nuke` and `make clear-*` are destructive: ask first.

---

## 8. Logging & Observability

- Use `src/logger.py`. Structured, contextual messages; include operation and element pair.
- Never log secrets or full LLM prompts at INFO or above.

---

## 9. AI-Assisted Development Rules

1. Inspect before you edit. Make the smallest complete change.
2. Add or update tests. Run `make check` before declaring done.
3. Review the final diff. Update docs the change touches.
4. Never claim a command passed unless its output was shown.
5. Never fabricate results, skip failures, weaken lint or types, or add placeholder code.
6. No unrelated refactors. No destructive commands without authorisation.
7. Ambiguous and it affects correctness: ask one focused question. Otherwise state the assumption and proceed.

---

## 10. Definition of Done

- [ ] Requirement met; existing architecture respected
- [ ] Failing test written first, now green; edge and failure paths covered
- [ ] `make check` passes (lint, typecheck, test)
- [ ] Docs updated where behaviour changed
- [ ] Diff reviewed; no secrets or unrelated files
- [ ] Known limitations written down

---

## 11. Final Principle

Build as if another engineer maintains this for five years. Quality is part of the implementation.

---

## 12. Project: Alchemy Crafter

Single-player infinite alchemy game. Combine two elements → new element generated by local Ollama on first discovery, then cached and persisted forever. Stack: Python, `uv`, FastAPI, PostgreSQL (psycopg2), Redis, Ollama via `httpx`, Docker Compose.
Everything above is universal. This section is project-specific and wins on conflict.

- Docs describe what exists. Target state belongs only in ROADMAP and sprint PRDs.
- Link with anchors (`path/doc.md#section`), paths relative to the linking file.
- A changed decision gets a new `D-NNN` that supersedes the old one.
- Behaviour change → update the owning doc in the same PR. Counts (tests, endpoints) are not hand-copied; link instead.

### Sprint workflow

1. Plan: raise doubts first, then write `docs/sprints/Sn/PRD.md` and `TODO.md`. Log decisions in `docs/DECISION.md` as `D-NNN`.
2. One branch per sprint, `feature/sN-<slug>`, from `master` ([D-007](docs/DECISION.md)).
3. One commit per TODO task, conventional messages enforced by the commit-msg hook. Per task: failing test → minimal code → green → refactor. The fix, its test and the TODO tick share one commit.
4. Before each commit: `make check` green. Hooks reformat on commit; `git add` the changed files again and commit again.
5. PR to `master`, CodeRabbit review, merge. Tick the backlog item.
6. Sprint end: review the sprint diff against ARCHITECTURE.md and the Definition of Done; write a handoff note.

### Author rules

- Python and tool versions come from `pyproject.toml`. Use `uv`; run via `uv run` or the `make` targets.
- Element pairs are always normalised and sorted (`validate_inputs`) before any cache, DB or AI call.
- Element names produced by the AI are single lowercase words, letters only, 2–30 chars, never equal to an input.
- Cache and context operations in `src/cache/` fail silently and never raise. DB and AI failures must not be swallowed: raise or log with context.
- Pipeline order is fixed: validate → Redis → Postgres → Ollama → persist (DB, cache, context). Do not reorder.
- `elements` and `recipes` use `ON CONFLICT DO NOTHING`; `recipes` is unique on `(element_a, element_b)` with `element_a <= element_b`.
- Never interpolate raw user text into SQL, Redis keys or the LLM prompt without validation.
- Unit tests run offline: mock Ollama, Redis and Postgres. Integration tests need `make up`.
- Never run `make nuke`, `make clear-all`, `make clear-db` or `make clear-redis` without being asked.
- Never `pkill -f` a pattern that appears in your own command text.
- `main.py` and `src/game/` stay thin: game logic belongs in `combine()` and `GameState`, not in CLI printing code.
- Run `make tree` after adding, moving or deleting files. Never edit `docs/STRUCTURE.md` by hand.

### Known deviations from the target design

Docs and code differ here today. Verify in code before relying on either.

- The concurrency lock lives in `src/api/routes.py`, not in `combine()`. The CLI bypasses it. The release is not token-checked.
- API routes are `async def` but call blocking code (psycopg2, sync `httpx`, `time.sleep`).
- The 404 existence check runs only in the API, not in `combine()` or the CLI.
- `OLLAMA_TIMEOUT` defaults to 100s while the documented AI target is under 2s.
- `_VALID_OUTPUT` in `src/ai/generator.py` is unused; the parser applies its own regex.

### Working with the maintainer

- Doubts first: ask before creating or changing files.
- Need a file, code or CLI output? Ask in a blockquote list (`> path` or `> command`).
- Every code block, command, script and diff names its target file by path relative to the repo root (header line, `# target: path`, or diff header). Unlabelled code is not allowed.
- Command blocks never contain `cd`: the maintainer's shell keeps the directory and the next
  block breaks. Everything runs from the repo root, for example
  `uv run pytest tests/test_x.py --no-cov` for one file.
- File changes: git diff for text and docs, `uv run python - << 'PY'` mutation script for computed edits.
- If `uv` warns that `VIRTUAL_ENV` does not match, add `--active` or unset `VIRTUAL_ENV`.
- Never claim a command passed unless its output was shown.
- Mutation scripts check every `old` string (exactly one match) for all files before writing
  any, so a failed assert leaves the tree untouched.
- Test first means the pasted red run comes before the fix.
- Tick a TODO task only after its verification output was shown.
- Hand-verified runs (Docker health, restart keeps progress) are recorded once in ARCHITECTURE
  with the date.
